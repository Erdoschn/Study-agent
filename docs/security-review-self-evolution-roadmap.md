# 安全审查与双 Agent 自我进化路线图

审查日期：2026-10-13  
审查类型：静态代码审查与现有测试覆盖审计。不是渗透测试，也不代表已验证真实浏览器和部署环境。

## 执行摘要

仓库已经有不少有效的纵深防御：StudyAgent 的工具采用 allow-list；Coder 的文件访问经过 workspace 边界检查；Python 在隔离 Docker 容器中运行；容器禁网、只读根文件系统、非 root 用户、丢弃 capabilities、限制进程数/内存/CPU/输出并支持超时；模型工具输出被标记为不可信内容；上传尺寸和前端 Markdown 渲染也有边界检查。

但**当前不能把系统视为经过全面安全认证**。最优先需要注意的是旧版 API 的远程绑定保护不一致，以及主 StudyAgent API 缺少请求体大小上限。默认监听地址是 loopback，这会降低默认暴露面，但不能代替远程绑定时的安全控制。

本次先盘点了仓库的完整文件树，再对主要信任边界及其关联测试进行定向静态审阅：包括 core 中的工具执行/模型路由/证据状态，tools/search 的网络请求路径，config 加载，examples 中的 API 外壳，coder 的 Harness/文件系统/沙箱，web 前端、依赖清单与 CI 工作流。本文不能替代逐行形式化验证或渗透测试，也不声称每个业务分支均已被动态执行；真实 Windows Edge、部署网络、实际凭据配置和第三方网页行为仍需实机验证。

## 风险清单与建议

### S-01 — 旧 API 远程绑定缺少强制认证门槛

**优先级：高（当服务绑定到非 loopback 地址时）**

相关代码：
- examples/study_agent_api.py：HOST、API_KEY、Handler._authorized() 和服务器启动流程。
- examples/coder_web_api.py：HOST、API_KEY、Handler._authorized()、_cors_headers() 和服务器启动流程。

这两个 API 的默认 Host 是 127.0.0.1，但 _authorized() 在 API Key 为空时直接允许请求；与较新的 examples/deepseek_web_study_agent_api.py 不同，旧入口没有在启动时统一拒绝“非 loopback + 空 Key”的组合。Coder API 还发送 Access-Control-Allow-Origin: *。如果有人把 Host 改成 0.0.0.0 或局域网地址却忘记配置 Key，StudyAgent 端点可能被用于消耗模型资源，Coder 端点的风险更高，因为它能读取/修改配置的 workspace 并启动受限代码执行流程。

**建议：**
1. 三个 API 统一使用经过测试的 _require_auth_for_non_loopback_bind()；非 loopback 必须有强随机 Key，否则拒绝启动。
2. Coder UI 若只作为同源本地网页使用，应把 CORS 收紧为明确允许的本机 Origin，而非通配符；不能用 CORS 代替认证。
3. 远程访问优先放在带 TLS 和认证的反向代理后。不要在不可信网络上直接传输 Bearer Key。

### S-02 — 主 StudyAgent API 未限制 JSON 请求体大小

**优先级：中；若远程可达则升高**

examples/study_agent_api.py 的 _read_json() 直接根据 Content-Length 读取请求体，没有硬性最大字节数。超大 JSON 会导致不必要的内存消耗；ThreadingHTTPServer 也意味着连接可对应独立线程。其默认绑定本机可降低远程攻击面，但在需要 LAN / Docker 网桥访问时应先修复这个边界。

examples/deepseek_web_study_agent_api.py 已有总请求体上限、文件数量与大小限制；Coder API 的 JSON 和文件上传也有上限，建议把主 API 对齐到相同的 fail-closed 模式。还应考虑读取超时、并发请求上限和请求队列上限，避免慢速连接或大量并发请求拖垮本地服务。

### S-03 — API Key 与上传内容的传输信任边界

**优先级：中（条件风险）**

本地 loopback HTTP 常用于开发；如果将服务绑定到外部接口，普通 HTTP 不会加密提示词、Bearer Key 或上传内容。StudyAgent 的 Web UI 会将用户选中的原始附件发到本地 API，然后再通过登录的 DeepSeek Web 会话上传给第三方处理。因此，“本地 API 接收文件”不等于“文件没有离开本机”。

**建议：**保留清晰的隐私提示；敏感文件默认不自动上传；远程部署使用 TLS；不要把访问 Key 持久化在 localStorage 或日志中。当前 StudyAgent Web UI 的 Key 保存在页面内存并清理旧的 localStorage Key，这个方向是正确的。

### S-04 — 前端 CDN 脚本与内容安全策略

**优先级：中**

web/index.html 依赖 CDN 上的 Marked、DOMPurify、highlight.js 和 MathJax。Markdown 输出经过 DOMPurify 清洗，并在清洗库不可用时退回 HTML 转义，这是一项重要防护。不过，脚本资源没有 SRI 完整性固定，也没有严格的 Content Security Policy；一旦被信任的脚本源或发布链路出问题，前端代码可以接触当前来源下的对话内容和内存中的 API Key。

**建议：**考虑将脚本随应用一起版本化发布或使用 SRI；逐步增加 CSP（需要先处理现有 inline script/style）；对 DOM 插入点继续使用 textContent，避免把任何状态文本直接拼进 innerHTML。

### S-05 — Workspace 文件系统的并发/TOCTOU 关注点

**优先级：中低，需针对威胁模型验证**

coder/filesystem.py 已拒绝绝对路径、..、符号链接及 Windows reparse point，限制读写扩展名和敏感文件，并采用临时文件 + os.replace() 原子写入。这些防护良好。

仍应关注：在多个本地进程能同时修改同一 workspace 的威胁模型下，路径检查与文件操作之间可能出现检查后状态变化（TOCTOU）问题。当前线程锁只保护同一个 WorkspaceFS 实例内的写入，不能串行化外部进程的文件系统操作。

**建议：**把自我进化任务放在专用、短生命周期的临时 clone/worktree；限制该目录的本机 ACL；评估是否需要更强的目录句柄式安全操作。不要把运行中的 StudyAgent 安装目录设为 Coder 目标目录。

### S-06 — Prompt Injection 与跨 Agent 信任

**优先级：中**

检索网页、用户上传文件、测试输出和仓库文档都可能包含恶意指令。Coder 已将部分工具输出放在 UNTRUSTED_TOOL_OUTPUT 边界中并做主机路径脱敏；StudyAgent 的 ToolExecutor 使用 allow-list，避免把 shell/文件修改能力直接暴露给学习 Agent。它们能缩小风险，但不能保证模型不会被内容说服去做不合适的事。

**建议：**把模型输出始终当作不可信的“建议”，而不是权限授予。每个变更都要经过确定性的 Harness 参数验证。自我进化阶段尤其不允许模型自行扩大权限、修改安全策略后立即运行，或把外部文档的指令提升为系统级策略。

### S-07 — 沙箱隔离：已有控制较好，但不是绝对保证

**当前状态：正向控制，仍需持续回归**

coder/sandbox.py 使用固定本地镜像、--pull=never、非 root UID、--network none、只读根文件系统、只读 workspace staging 副本、--cap-drop ALL、no-new-privileges、PID/内存/CPU/文件描述符/输出上限以及超时。staging 还排除 .env、私钥、备份目录和非允许扩展名。安全测试会验证部分主机文件、Docker socket 和网络不可达约束。

注意两点：第一，真实沙箱测试在未构建镜像时会被跳过，所以 CI 必须保留专用的镜像构建与安全测试 Job；第二，Docker 引擎、宿主机账户和 staging 过程依然属于可信计算基，不应把沙箱宣传为完美隔离。

### S-08 — 依赖与 CI 供应链

**优先级：中低**

requirements.txt 使用版本范围而非完整 lockfile；GitHub Actions 采用 @v4 / @v5 这样的主版本标签，而非不可变 commit SHA。这样较容易升级，但无法保证每次构建使用完全相同的依赖集合或 Action 实现。

**建议：**增加定期依赖更新和漏洞告警；对部署/发布所用依赖生成 lockfile 与 hash；高保证工作流逐步将 Actions 固定到经过审核的完整 commit SHA；对依赖升级运行完整测试、沙箱安全测试和端到端冒烟测试。

### S-09 — 调试日志与本地数据残留

**优先级：中低，取决于本机使用方式**

启用 debug 时，部分模块会记录检索参数、证据标题/主张、路径和工具参数。一般日志用于本机诊断，但如果将终端输出保存、共享或上传，可能包含用户研究问题、代码片段或其他敏感上下文。Web UI 还会将对话文本与历史附件文件名保存到浏览器 localStorage；附件二进制本身不会通过该机制持久保存。

**建议：**增加显式的日志脱敏级别和保留策略；分享日志前先脱敏；提供清除本地对话记录的操作说明。不要把原始附件字节、API Key 或完整提示词用于状态流。

## 已观察到的有效安全控制

- StudyAgent 工具执行器有明确允许列表，计算器使用受限表达式处理，而不是通用 Python eval / exec。
- 模型路由默认禁用付费模型，除非调用方明确允许。
- 原始附件通过大小/数量限制与文件名校验后传递；前端与 API 不把附件正文直接拼进提示词。
- Coder 的路径政策、文件扩展名、Notebook JSON 校验、原子写入、参数校验和独立 workspace 边界覆盖了多类越界风险。
- Python 执行在只读 staging 副本中运行，容器没有网络；Harness 不让模型自行生成任意 shell 命令。
- Web UI 使用 DOMPurify 清洗 Markdown，并在清洗库缺失时 fail closed。
- 对不可信工具输出、沙箱边界、附件上传与会话清理都有回归测试。

这些控制值得保留；重点是把分散的安全规则转化为启动时不变量和持续 CI 约束。

## 推荐整改顺序

1. **P1：**统一三个 API 的远程绑定认证要求；修复主 StudyAgent API 的请求体大小/超时边界。
2. **P1：**新增统一的 API 安全配置测试，覆盖 loopback/非 loopback、空 Key、错误 Key、非法/过大的 Content-Length。
3. **P2：**收紧 Coder CORS、建立 CSP/SRI 计划、日志脱敏与数据保留说明。
4. **P2：**依赖锁定/自动更新；保持 Docker 安全测试独立、必需执行。
5. **P2：**建立真实 Edge + DeepSeek 的可选端到端验收集，覆盖登录、发送、附件、会话清理、限流与断线恢复。
6. **持续：**对文件系统的并发路径竞态做定向测试；对 Prompt Injection 建立红队样本并确保工具权限仍由 Harness 决定。

以上高优先级项目应在开放局域网访问或构建自我修改自动化之前完成。

## StudyAgent + Coder 协作的自我进化方案

### 核心判断

**可行，但应定义成“自动研究、自动生成候选改动、自动验证、人工批准合并”的受控改进流水线，而不是不受约束地让 Agent 修改自己的运行时并自行部署。**

StudyAgent 适合研究和分析：读取问题报告、历史失败、论文与文档，形成可验证的任务规格、风险假设和评估指标。Coder 适合受 Harness 限制的工程执行：在临时 workspace 中修改实现、补测试、运行 pytest、观察失败并修复。两者互补，但不能把其中一个 Agent 对另一个 Agent 的肯定当作独立安全证明。

### 建议架构

失败记录 / 用户反馈 / 基准测试 / 研究文献  
↓  
StudyAgent：研究与问题规格（复现步骤、证据、验收条件、风险）  
↓  
Candidate Task：结构化任务单  
↓  
Coder：隔离实现与测试（临时 clone/worktree、小范围修改、回归测试）  
↓  
独立验证门（全量 pytest、沙箱安全测试、静态扫描、固定基准与隐藏回归集）  
↓  
生成分支 + Pull Request + 变更说明  
↓  
人工代码审查与合并  
↓  
合并后观察结果，更新实验记录

### 分阶段实施

**阶段 0：只读研究。** StudyAgent 定期分析失败日志和测试报告，只输出排序后的改进建议、证据、风险和验收指标；不写仓库，不创建自动修复。

**阶段 1：受约束的候选补丁。** StudyAgent 生成一份结构化任务规格。Coder 在独立的临时 clone 中工作，仅修改任务允许的路径，必须增加或更新测试。改动默认限制为较小的文件/行数范围。

**阶段 2：自动验证并提交 PR。** 自动运行 pytest、沙箱安全测试、静态安全检查和固定基准集；任何安全测试失败、测试回退、范围越界或关键配置修改都阻止 PR 进入 ready 状态。Agent 可以创建分支和 PR，但不具备合并、发布或删除分支的能力。

**阶段 3：有数据的反馈循环。** 只有候选补丁被人工审查并合并后，才对其做真实任务评估。记录变更前后的成功率、无效工具调用、耗时、证据质量、回归数和用户反馈。若表现退化，生成回滚建议，而不是自动覆盖主线。

### 两个 Agent 的职责边界

| 角色 | 负责 | 不应拥有 |
|---|---|---|
| StudyAgent | 故障分类、外部资料检索、研究假设、验收条件、结果分析 | 直接修改生产安全策略或给自己的补丁盖章 |
| Coder | 任务范围内修改代码、生成测试、在沙箱中运行验证、输出 diff | 任意 shell/网络、读取宿主机凭据、直接修改运行中的 Agent 安装目录 |
| 确定性 CI / 独立验证器 | 执行固定测试、静态检查、基准评分、范围检查 | 将通过测试解释为“绝对安全” |
| 人类维护者 | 审查高风险 diff、批准合并与发布 | 不建议把审查权限交给自动循环自身 |

### 防止自我进化退化的关键设计

- **不可变安全不变量：**候选代码不能自行降低测试要求、禁用安全检查、扩大工具 allow-list、修改评分门槛后再声称通过。
- **评估数据隔离：**把部分基准/回归用例保存在候选分支不可修改的位置，避免 Coder 为通过测试而修改测试答案。
- **权限分离：**Agent 的 GitHub 凭据仅允许创建分支和 PR；不授予合并、删除分支、管理 Secrets 或发布权限。
- **独立验证：**不能只让写代码的 Coder 自己判断代码正确。用确定性测试、安全门和固定基准做交叉验证。
- **限制影响范围：**安全敏感文件（API 认证、文件系统边界、沙箱、CI、依赖配置）自动标记为高风险，必须人工审查。
- **可复现的实验记录：**保存候选任务、commit、测试结果、依赖版本、评估指标和人工决定，确保能够解释每次改进。
- **停止条件明确：**测试失败、验证结果不确定、预算耗尽、范围越权或安全扫描发现新问题时，保留失败现场并停止，不以“继续自我修复”无限循环。

### 应如何衡量“进化真的有效”？

单纯增加代码行数、通过现有测试或让模型自评“更聪明”，都不足以证明进化有效。应使用固定的任务集进行版本对比，至少记录：

- 端到端任务成功率与回归率；
- 每个任务的耗时、模型调用量、检索次数和成本；
- 证据充分性、答案准确性与不确定性表达；
- Coder 补丁的首次测试通过率、修复轮数和越界尝试数；
- Learner Model 是否改善后续任务表现，而不只是改变回答措辞；
- 安全测试是否全部通过，以及新版本引入的风险和人工审查成本。

最终目标不是“Agent 自己改自己”，而是形成一个**可测量、可复现、可回滚、可由人类控制的研究与工程改进循环**。这既能发挥 StudyAgent 的研究与分析能力，也能利用 Coder 的执行能力，同时不把整个项目的安全性押在模型自我判断上。
